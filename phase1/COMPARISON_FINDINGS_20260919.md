# 学长新 ForeTS/MCTS 对照：独立复核与下一步收益实验

日期：2026-09-19。原始 ForeTS 实现、训练和比较数据来自学长；本文为我方独立复核。已先读学长报告，因此是探索性分析，不冒称预注册确认实验。

## 一句话结论

新数据已经拿到并完成逐 run 复核：目前不能确认 ForeTS 有稳定的同预算收益，也不能凭两个重复块均值接近就排除随机性。最有用的新资产是 **25 个完整的六候选初始池**，能把下一步问题缩小为“候选是否有机会，critic 是否把机会选出来”。这比继续盲目扩展 E2E 配方更直接，但仍须真实执行未选程序，不能把资产本身写成方法收益。

## 2. 真实 run 级结果

差值均换成“正数有利于 ForeTS”的方向。只配对相同 seed、任务、生成器和标称预算；**硬件及实际总 GPU 成本尚未配平，所以不是因果确认**。每个独立 run 算一个样本，不把节点数当样本量。

| 对照层 | 可读共享 seed 数 | ForeTS 胜/负 | 差值中位数 | 差值均值 ± SD |
|---|---:|---:|---:|---:|
| Pizza，ForeTS-1 vs MCTS | 5 | 2 / 3 | −0.007720 | −0.021710 ± 0.128539 |
| Spooky，ForeTS-1 vs MCTS | 5 | 1 / 4 | −0.031300 | −0.026918 ± 0.046591 |
| Leaf，ForeTS vs MCTS | 3 | 2 / 1 | +0.009910 | −0.105163 ± 0.252259 |
| AI4Code，ForeTS vs MCTS | 1 | 1 / 0 | +0.023180 | +0.023180，SD 不可估 |

AI4Code 另有 2 个共享 seed 因 journal 缺失不能比较。Pizza/Spooky 的 ForeTS-2 用 seed 9–13，而 MCTS 用 1–6，不能当作更多配对样本。各任务指标尺度不同，不能把这些原始差值平均为总体收益。

描述性双侧 sign test 的 p 值依次为 1.0、0.375、1.0、1.0；这些小样本结果既不是“稳定胜出”，也不是“等效”证明，更不能支持“已经排除噪声”。

Leaf 尤其说明为什么不能只看均值：三个共享 seed 中 ForeTS 赢两个，但另一个大幅落后，使均值与中位数方向相反。与此同时，全组 checkpoint 的记录运行时间均值约为 ForeTS 22.20h、MCTS 9.93h，不能把上述两胜包装成同预算获益。

## 3. 影响解释的具体事实

1. **配置并不统一。** 五包中既有 ForeTS 6 候选/top-3，也有 9 候选/top-2、8 候选/top-1 或 top-4；另有 39,600s、82,800s 与 86,400s 等不同搜索上限。本文数值只来自新的 Qwen 分层，未混入旧 API 层。
2. **原绘图与 solver 选择语义存在潜在差别，但没有改变这批读出。** 绘图用官方指标方向处理内部指标，且未显式做 buggy 过滤；solver 使用内部指标自己的方向并过滤 buggy。43 个可读 journal 中实际选中节点均相同，不能把源码差别夸大为本次胜负翻转。
3. **曲线与终点需要区分。** 原绘图按节点创建时间定位，而非已验证的执行完成时间，且整小时截断会略去最后不完整区间。本文用全部 checkpoint 节点，不声称逐字复现报告中每个曲线末点；在完成时间证据齐全前不补画“严格同时间”曲线。
4. **RL critic 的 63.37% vs BT 的 60.01% 不能直接归因于 RL。** 两者模型规模、验证覆盖及 checkpoint 选择不同。这是学长报告中的探索信号，不是我方新的 matched 算法收益。
5. **官方事后最优只作诊断上界。** 它不能作为部署可用的选择器，内部/外部分数的不同尺度或不同节点最大值差，也不能直接认定为 reward hacking。

## 4. 能实质推进方法的新资产

找到 25 个结构完整的初始池：Pizza 10、Spooky 10、Leaf 3、AI4Code 2。每池有 6 个候选，其中原来执行 2 个、未执行 4 个；共 150 个候选，含 **100 个尚未执行的初始候选**。全部搜索阶段合计保存了 480 个未选节点。

每个初始池的 6 份原始代码哈希均不同。这里只证明字节不同，**不证明语义多样性、有效性或质量上界高**。另一个 AI4Code ForeTS run 没有 journal，保留缺失。

这批数据允许不用新生成 API 就准备完整同池执行：

- 候选供给：六个程序中是否存在有效解、是否存在有意义的质量差？
- 筛选机制：原来选中的两个，相比六选二的均匀策略是否更好？
- 可挽回空间：原来丢弃的四个中是否有更优可执行程序？

journal 顶层没有原始 critic rank/value 字段。历史源码表明分数写入日志，但日志恢复、候选对应关系仍需另核；不能用异步完成顺序猜排名，更不能重新打分后声称是原来的排名。结构候选清单已经保存，**不是已执行 replay，也不是新 GPU 预算批准单**。

补查回执：46 个新 Qwen run 的归档成员只有配置、环境文件、`JOURNAL.jsonl`、grading report 和 checkpoint 文件，没有文本日志。源码写入 critic 数值的 info 日志未随这些包提供；环境文件未打开。当前不能恢复完整原排名，但两个已执行候选的身份已知，因此不妨碍准备“原选二 vs 同池均匀二”的对照。未核原排名前不报告 top-3 召回率。

## 5. 推荐的推进判断

保持目标为 **固定生成器、同总资源的最终质量收益**，不把“无 API 账单”或“多生成几个候选”本身当正结果。27B INT4 是学长为降成本采用的本地替代，“更弱”是学长判断，不是我方已完成的跨模型测量。

优先进行有限的完整候选池验证，而非再次扩大未经复现的短代码/门控配方。池的选取按任务、时间、seed 的结构规则固定，不按已看到的胜负挑选；完整执行六个候选，保留失败与基础设施未知，并核原镜像、数据、执行时限。未选程序执行仍有真实 GPU 成本；7200s 是单程序上限，不能称“免费”。

只有观察到可重复的同池选择收益，才进入 fresh-seed E2E；同时保留不使用 critic、能利用节省资源的系统基线。若六候选普遍都差，重点应转到可执行候选供给，而不是继续调排序阈值；若存在好候选却选不中，才有依据改进 critic 的目标或使用方式。

这些是可证伪的下一步，不是本轮已经得到的正收益。原始排名恢复结果另见对应回执；不恢复关闭的 HCE、多保真、Probe、score-channel 或 K≥1 路线。
