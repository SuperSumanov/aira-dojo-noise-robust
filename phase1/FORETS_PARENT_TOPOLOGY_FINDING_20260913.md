# 当前控制器实际搜索了什么：单链，不是分支选择收益

2026-09-13 HK。仅分析已经闭合的 seed26/27 八次开发搜索；不读取运行中的 seed28/29 最终成绩。

## 已验证的事实

- 四次 Space 搜索都有完整 journal，各自 7、8、7、9 个保存节点，均只有一条根到叶链：
  每个节点最多一个子节点，分叉、悬空边、不可达节点均为零。四次 Leaf 没有完整 journal，不能算作空树。
- 实际 source `fb2c041c8ec8e352847881ee6fe2fb56d9561aec` 中，ForeTS 继承 MCTS 的逐子节点 UCT 遍历；
  每轮候选池只执行一个选中程序。未执行候选不进入真实树，这一点是正确的，不能补造节点成绩。
- debug 节点通过 `Node.__post_init__` 自动连接父节点；没有“修复节点未接树”的证据。
- 只有一个子节点时，UCT 的最大值选择没有分支可选。实际导入生产类的 CPU 结构测试中，
  `uct_c=0/1/100` 都到达相同坏叶子，而只用搜索可见验证分的 incumbent 参考返回已有好父节点。
  这是结构测试，既不是重新执行候选，也不是改善最终成绩的证据。
- Space random seed27 的一次后续扩展确实选择了内部标记 buggy 的父节点，而此前已有内部标记非 buggy 的节点。
  其余有 journal 的运行未观察到该模式；`is_buggy` 不是外部提交有效性，不能推导反事实收益。

因此，目前的选择对照是“单链上的候选筛选”，不能表述为已经证明 critic 改善多分支 MCTS。
这不使候选筛选对照本身失效，但限定了机制解释和结论范围。

另外，对同一闭合包全部 candidate ledger 的计数排除了“候选普遍是完全重复代码”的解释：
random 共14池、56次生成全部返回、14次原候选执行；critic 共11池、44次生成中40次返回、10次原候选执行。
两臂分别仅有一次池内字节完全相同代码。计数按每池保存代码数减唯一代码数计算，不是AST/语义多样性。
random 的56个返回程序中14个得到执行，因此单候选直接执行是应补的成本强基线；
但并行生成时间不能乘四当总时长，未执行程序费用也未单独核定，不能把其余42个称作已证明可节省的墙钟时间。
