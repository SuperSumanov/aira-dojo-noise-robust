# 参考反馈方向：已有先例与真正需要验证的部分

2026-09-13；本轮核对原论文，不把新提示词称为新算法。

[CEB原文](https://arxiv.org/html/2607.12397v1)已经把历史执行经验放进冻结critic，并同时使用当前轨迹历史。
其主结果是置信度与排序；§4.5为离线筛选/模拟oracle纠错，附录G为固定状态下再生成。
因此“critic看过去执行反馈”本身明显有强相关先例，不能宣称我们首先提出；也不能据此说其结果已解决真实MLE闭环同预算搜索。

我方待验证的是较窄问题：程序执行成本远高于生成时，候选相对当前已交付解的改进判断，能否扣除裁判开销后提升最终提交。
现成的参考提示首先作为机制基线，不是论文核心创新。当前两臂只能回答参考critic与随机的差异；若有效，下一步必须加入
同源无参照critic和单候选直接执行的强基线，才能区分参考信息价值、筛选价值与额外生成成本。

真正值得争取的正发现应至少满足：不是只提高离线排序；不是只避免首个无效提交；在已有可行解上有额外收益；
多个seed、任务和合理预算下收益超过选择成本。若只在某个任务/seed出现，作为定位问题的线索，不升级为稳定结论。

目前已知缺口仍包括任务范围窄、生成代码失败多、程序时长相对600秒总预算过大、完整迭代提交边界。
这几项需区分处理，不能一次全改再把进步归功于critic。新32/33候选协议只改变critic所见历史参照；
不改变当前30/31运行，不回收未执行候选的虚构成绩，不恢复多保真/早停/隐藏分选解。

另一个待测而非已证的方向是原子动作交付：如果第一候选已完成却因第二候选未完成而不被提交，
需在未来轨迹同步记录“逐动作”与“整迭代”两种原搜索可见选解，不对当前结果追溯改判。
这是可交付性机制与实现问题，不能单靠保存文件主张新算法；外部成绩也不保证提高。
