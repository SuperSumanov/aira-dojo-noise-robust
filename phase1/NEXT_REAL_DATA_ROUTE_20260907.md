## 为什么不能把现有大文件直接送进正式训练

历史记录仍没有足够证据认证实际 pristine evaluator/runtime。当前固定范围的 grading metadata 未提供版本字段，
也未找到保留的 submission 预测表，因此不能在不重执行的情况下直接用今天 grader 重新算出那些标签。
这不是 GPU 排队问题，也不是请学长再上传同一份 Cards 就会自然解决。

原 84 run 包含 24 个保守组件、15 个任务；其中仅 6 个任务至少有两个组件。
这只是同任务 train/dev 覆盖的必要支持，不是功效证明。不得按未来成绩选任务，
也不新增“train/dev 必须完全同配置”这一要求；pair 内 exact-stratum 和跨配置泛化是不同问题。

## 两条可行来源路线，不混淆事实

1. **找回实际已有评分出处**：若生产端尚有安装/镜像/外部评分记录，提供原记录位置即可；
   不要求手填 JSON、不要求找回已删 snapshot，也不接受今天 SHA 代填过去。
2. **原有程序，今天完整重新执行与评分**：从历史 run/experiment 闭包固定程序，
   原代码字节不改，使用今天固定的执行环境与独立 grader，产生新的执行标签。
   这应明确命名为新的历史程序重执行开发数据，不能声称复现原分数、修复旧 S0 或替代前瞻确认集。

第二条不是低保真筛选：不得先给部分预算、根据早期分数追加时间；所有候选的完整执行上限在运行前固定，
所有超时/错误/无提交均保留。它需要新的成本矩阵、选择前冻结、input/code/submission/grade 哈希链、
worker 只见 public 输入、private 答案仅供外部 scorer，才能实际开跑。目前尚未选候选或启动该路线。

环境方面，已确认镜像内无 `mlebench` distribution；应使用独立固定来源的外部 grader，
不能让候选 workspace 内的脚本充当 evaluator。当前可读 MLE-bench Python 代码与记录 commit
`507f92e1138bb6e40dac5c6ee7a6758e6424bf97` 的 187 文件相同，但未认证整个工作树或过去环境。
源码检查还确认当前 `Grader.__call__` 将结果舍入至五位小数；新标签回执需要保存这个精度语义。
这不证明每一条旧记录都由该版本产生，也不允许更改已有标签或结果后调整 gap 门。
