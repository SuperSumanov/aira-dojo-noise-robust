## 这次解决什么

现有 `LocalGpuPoolLauncher` 分配的是整次搜索 run 的整卡槽位，`ExecutionResult`
主要记录执行时长。它们不能回答候选在何时使用 CPU/GPU、是否出现晚发资源峰值。
先建立可审计观测接口，再决定调度方法；不能从最近失败程序或启动器低占用推断共享收益。

`observe.py` 只读取明确提供的同用户 PID 及分配内的完整 GPU UUID。
PID 必须连同启动 ticks 和宿主 boot ID 提供；不扫描其他进程、不读取命令行/环境变量/
候选代码/标签/日志。不启动、停止或改变任何目标进程。

- CPU：指定进程的累计 ticks、线程数；相邻有效身份的 CPU 秒差值。未覆盖子进程。
- RAM：指定进程的近似 RSS，不等于独占内存，也不是整个候选的内存上限。
- I/O：内核 storage read/write/cancelled-write 计数，不等于逻辑 I/O 或网络带宽；文件系统影响语义。
- GPU：显式设备的显存和利用率，**整卡测量，不是该候选的占用**。不提供每进程 GPU 利用率。
- 时间：每次采样前后 monotonic 时间、UTC、采样墙钟开销；间隔为采样完成后等待，非精确固定频率。
- 复现：调用方源码 commit、记录器 SHA256、内核/Python 版本、单位和目标身份。

缺失/权限不足/不支持不能填零。身份漂移或设备查询失败终止记录器并写不完整回执，
但绝不杀死候选。I/O 或单项 GPU 指标缺失保留状态；footer `complete` 仅表示计划采样结束，
不表示覆盖完整。输出独占新建，不能覆盖或追加旧结果。

## 运行与测试

仅在 Linux、持有可信 launcher 身份及设备分配信息时运行。不要从候选的文本自报获取身份。

```text
python phase1/sandbox_scheduling/observe.py \
  --pid <HOST_PID>:<START_TICKS> --boot-id <HOST_BOOT_UUID> \
  --source-commit <FULL_COMMIT> --output <NEW_PRIVATE_TRACE.jsonl> \
  --samples 30 --interval 2 --gpu-uuid <ALLOCATED_GPU_UUID>
python phase1/sandbox_scheduling/test_observe.py
```

不传 `--gpu-uuid` 就不调用 NVIDIA 工具。UUID 本身不证明使用权限，调用方须核对分配。
Linux 测试只观察测试进程本身约一秒，临时文件自动清理；不读现有实验数据，不调用 GPU。
Windows 的该测试明确跳过。`--receipt <NEW_JSON>` 保存带代码哈希的工程测试回执。
测试/仿真不构成共置安全、任务兼容、监控扰动或真实收益证据。

2026-10-06 已验证：[Windows 回执](validation_windows.json) 为22通过/1跳过；

## 生产接入尚缺什么

| 接口 | 已定位事实 | 接入要求（本轮未修改） |
|---|---|---|
| Jupyter 执行器 | server 长驻，kernel 可重建；工具返回不等于 GPU 上下文释放 | launcher 提供 kernel 的宿主身份及实际生命周期，不能只跟 worker/server PID |
| FreshContainer 执行器 | 独立进程组及身份发布，但属于另一个可选后端 | 可复用可信身份；不得为了易观测暗换对照后端 |
| 进程范围 | 子进程和 PID namespace 可能变化 | 需要可信进程树或专属 cgroup 归属，不能靠 PID 号猜；当前恒标记 `candidate_scope_complete=false` |
| 搜索生命周期 | 到达、执行、结束与回收是不同事件 | 调度器外侧记录 arrival/start/end/release、匿名候选 ID、并发成员；不能读取结果后定义 arrival |

v0 不是树级资源账本，不做短命子进程追踪；RSS 不跨进程相加作独占内存。
GPU 为整卡数据，出现其他租户/未归属进程时不能算本候选成本或剩余容量。
10/6六次固定无数据张量程序已完成真实GPU/原容器测量；仍未验收MPS/cgroup，
也未为任意MLE程序证明资源范围完整。见下方限定结果。

## 第一轮科学问题与对照草案（尚未冻结或获新 GPU 预算）

**优先问题：不知道下一阶段峰值、又不能廉价撤销共置时，事前资源判断是否有价值？**
先证明这种问题在真实生成程序里频繁且代价明显，再问代码语义是否比廉价规则提供额外信息。

| 对照 | 变化的唯一机制 | 必须排除的解释 |
|---|---|---|
| A0 run级固定整卡槽位 | 当前生成/执行均保留槽位 | 把run级绑卡开销误称语义增量 |
| A1 执行级整卡借还 | 只在任务执行/文件取回/核实清理期间持槽位，每卡至多一个执行者 | 普通阶段解绑定是否已经解释收益 |
| B 固定共享槽位 | 在A1上，每卡至多两个执行者 | 所有剩余收益只是并发数提高 |
| C 保守资源准入 | 同 B 并发上限，历史/当前遥测和静态特征判断准入，带 aging | 简单显存打包已经足够；短任务偏好导致饥饿 |
| 后续 D 语义/经验变体 | 同 C 执行控制器，仅需求估计变化 | 是否超过 SchedMate 式语义检索，而不只是超过 A |

这不是启动矩阵：真实程序清单、时长与总 GPU 小时尚未确定，不能提交。
首先用合法开发任务、固定筛选规则准备包含 CPU/神经网络/混合阶段的真实候选清单。
模型、代码、输入数据、镜像、GPU 型号、到达时间和每程序超时固定；写目录私有、数据只读共享。
失败候选按事前规则保留分母，不能只挑共置有效程序。不得读取封存 cohort 或官方 test。

先做固定到达流的真实执行 replay，避免新搜索分支带来混杂。初期只准入/等待/自然完成回收，
不抢占、不早停、不假设 SIGSTOP 释放显存。3090 不依赖 MIG；MPS 也不视为显存隔离保证。
同一共享机制须用于 B/C/D，不能 C 用不同镜像或减少训练量。

主报告固定工作清单在全资源成本下的完成时间、有效完成数、OOM/失败、最坏及尾部等待；
整池保留 GPU 小时包含空闲、初始化、监控及语义服务，不能累加进程时长代替。
固定清单须完成或到统一截止，不能用“完成更多便宜候选”冒充质量收益。
离线无匹配历史/晚发峰值压力条件预先标记，历史只来自过去或独立校准，不给方法未来峰值；
全信息 oracle 只能作另计成本的上界。重复执行用于复现，不冒充独立任务/训练 seed。

完整调用链已按执行关闭factory，因此A1不能额外改成新的kernel重启策略再与A0比较。
租约释放必须来自可信runtime的文件取回/进程清理确认，不能来自候选自报done/低利用率。
生成服务GPU数量、模型、并发上限固定并计入池预算；不允许A1靠免费增加生成算力获益。
请求积压/执行就绪队列长度也需测量；仅有可释放时间而无等待工作不是收益。
首次固定trace的结果仅限系统诊断；扩大在线活跃run数后的生成并发/超时/质量改变必须另测。

只有 C 有净收益且失败/等待风险可控，才考虑 D；若 A1或B已解释收益，结论归于简单机制，
不强行引入 LLM。若 D 不超过强参照，保留系统结果，不称新语义调度方法。
最终固定 generator/search 的 live E2E 另做；replay 提速不证明最终质量提高。

## 新颖性边界与语义参考

[SchedMate](https://arxiv.org/html/2510.03334) 已有源码语义、历史检索和干扰共置处理，
不能把“LLM 看代码调度”当新颖点。[ElastiCo](https://arxiv.org/html/2608.07971v1)
也涉及 GPU 共置。无可靠匹配、无统一进度/恢复接口的晚发峰值只是待验证窄点，尚无优势证据。

本轮还核到[Cortex的作者摘要](https://research.google/pubs/cortex-workflow-aware-resource-pooling-and-scheduling-for-agentic-serving/)
已有按工作阶段划分资源池；[SpecBox](https://arxiv.org/html/2607.23933) §3–5已有生成期间预热/跨步预取，
32种MCP服务/200条轨迹，目标包含CPU沙箱冷启动和host内存。这些限制“阶段解绑定/预热”首创说法，
但不替我们证明任意MLE程序的GPU共置收益。

[Agentic CPU-GPU Scheduling](https://arxiv.org/html/2607.22242) §3–5已有即时GPU/排队GPU/CPU三选、
测量反馈和交换重测；19工具离线每设备30次，13构造场景，推理另占GPU，部分结果取20轮最佳。
其S1–S10中UCB1与LLM均找到最优映射，不是LLM必胜经典策略的证据。
若我们声称适合一次性新生成程序，必须报告第一次及累计调度代价、失败损失，不能免费预profile
每个未来候选再报最佳一轮。不能静默把GPU任务改到CPU，因为硬件适配可能改变程序行为。

当前押注是**先证明存在可回收且有就绪工作能利用的窗口，再检验未知程序准入是否超过廉价方法**。
已有测量支持做小规模下一关，不足以认定语义有必要。生成吞吐、执行等待、完整工作清单完成时间
必须一起记录；整个生成/执行资源池、CPU配额与每程序限制保持不变。

字段语义依据 [Linux proc 文档](https://docs.kernel.org/filesystems/proc.html) 和
[NVIDIA SMI 文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)，不把 CPU/GPU 利用率当有效训练进度。

### 10/8增补：输入与近邻边界

- 全训练文件出现全部类别不保证交叉验证训练折覆盖。16989先缺唯一类5；16992补后另一类仅1行，原程序fallback KFold仍产生缺类。新fixture要求非5类至少5个不同公开行，唯一类5按原程序进每个训练折；排除query，不复制/重标，不改源码。这个修复不是调度收益。
- [Ready Cohorts v2](https://arxiv.org/html/2608.12123)已有ready供给与机会/实际收益区分；研究的是微型确定性控制转移，其零服务时间离线边界并非任意MLE执行收益。不能将“先看有没有就绪工作”称新算法。
- [SAGA](https://arxiv.org/html/2605.00528) §4–6已有工作流、KV缓存、tool TTL与任务公平性；非本试验任意候选GPU训练，但工作流感知本身不新。其收益数字不替代本地强参照。
- [ElastiCo](https://arxiv.org/html/2608.07971v1) §4依赖配置画像、框架参数及必要时checkpoint恢复；这些接口在自然MLE程序中是否具备要实测，不能假设任意程序可无代价撤销，也不凭适用性差别宣称新方法。
