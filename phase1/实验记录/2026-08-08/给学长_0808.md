学长,有三件事同步一下,其中第一件是我自己查出来的一个数据问题,得先说。

## 1. 我之前报的 L1 = 0.828 需要修正,真实值约 0.686

按你说的「训练数据构造要和树生长时选节点对齐」去做实验,顺着查评估严谨性,连锁挖出了一个我们一直没意识到的泄漏,分三层:

- 我们语料里 **44% 的卡片是「孤儿」**(父节点因为没跑出真分被剪掉了),所以一棵树在数据里其实碎成了很多片。我之前做的所谓「按树切分 train/test」,实际上是按**碎片**切分。
- 同一次物理 run 的碎片被分到了两侧。我按批文件的连续性把 run 归属重建出来了(457 个 run,两条独立校验都是 0 违例):**99.7% 的 in-task 测试对,和训练集共享同一次物理 run**。
- 拿这个分层去拆 L1 那个 0.8200:碎片混合的部分 0.8405,**碎片干净的部分只有 0.6859**。也就是说那 15 个点是「见过同一次 run 的其他节点」带来的记忆,不是泛化。

修正后的诚实叙事其实还是站得住的三段:全局技能真实但温和(~0.69)→ 被 run 身份放大到 0.84 → 到了真正的决策点反而塌掉(下面第 2 条)。而且**跨任务的 LOTO / 迁移表不受影响**(那本来就是任务级切分),它们现在和这个修正后的数字互相自洽了。

run 级干净切分的重训在跑,今晚出最终数字。我打算把「碎片化搜索树数据的 run 级泄漏:怎么发现、怎么量化、怎么修」单独写成数据集论文的一章 —— 这类东西 D&B / R&E 的审稿人是加分看的。

## 2. 你那三条建议的实验结果(核心发现:排序反转)

按你说的,我把训练对改成「同一个父节点下的兄弟节点之间比较」= MCTS 咨询时真实面对的决策。结果很有意思:

| 打分者 | 全局随机对 | **决策对(兄弟之间)** |
|---|---|---|
| 训练出来的 RM | 0.828 | **0.55**(三 seed:0.570/0.522/0.543) |
| agent 自己报的验证分(不用训练) | 0.635 | **0.727** |

三 seed 多数投票 McNemar **p = 3.4e-14**,而且分差越大自报分优势越大,所以不是「兄弟本来就难分」。**全局评估和部署决策点的信息排序是完全反转的。**

机制上说得通:RM 在全局池上赢,靠的是「这个节点属于哪条 lineage」这种身份信号;一旦条件在同一个父节点下比较,这个信号被消掉了,剩下的执行反馈本来就是自报分更强。这也顺带解释了我们之前 RM 引导搜索为什么是 null(p=0.75)—— 不是实现问题,是结构上必然。

你三条建议的答案:
- **①对齐训练**:做了,不是瓶颈。把全局训的 0.83 模型直接拿去打决策对也只有 0.548,和专门在决策对上训的 0.55 基本一样 —— 兄弟粒度的信息不在代码文本里。
- **②0.5B + 长 context**:试了 0.5B@6144 vs 1.5B@2048,**0.538 vs 0.573,长 context 反而更弱** → 瓶颈是容量不是上下文长度。
- **③in-task oracle**:就是上面这个,结论是在节点充足的任务上也不 work。

**唯一的正面口子**:问「哪个孩子会通向更好的子树」(K≥1 前瞻)时,RM 反超自报分(0.645/0.651 vs 0.559/0.581)。也就是说 RM 唯一赢的地方,恰好是执行反馈原则上答不了的那个问题。而且所有方法在这上面都很弱 —— 这正好可以作为数据集论文抛出的 open problem。
