## 二、主要新进展：pair weighting 会扭曲 benchmark 的任务权重

### 2.0 新增的时间序与机制验证

在本报告最初的 first-240→339 端点比较之后，我们先冻结时间点、机制分解和四个 kill/claim gate，再读取完整轨迹。正式
双实现结果表明：

- 260/280/300/320/339 共 `5/5` 个晚期检查点均保留“run-HHI 下降、pair-HHI 上升”的反转；
- `30/30` 个 leave-one-task-out 及删除当前 pair-dominant OSIC task 后，反转方向仍保留；
- Shapley 分解中，task-specific opportunity yield 解释 pair-HHI 增量的 `64.47%`、run→pair TV 增量的 `59.51%`；
- 但 0820 OSIC 的一个 5-run 批次解释了 `96.42%` 的 pair-HHI 增幅，预注册的“无单批次 artifact”门失败。

因此更新后的最强表述是：**反转符号可泛化，幅度对高产率批次敏感；decision-opportunity yield 是主要机制。** 删除该
5-run 批次后，run-HHI 仍下降、pair-HHI 仍上升，但后者增量仅为 `+0.001888405775504004`。这既把端点相关推进成了
时间持续性与机制证据，也明确保留了批次 leverage 的负面边界。

还有一个不依赖 outcome 的严格推论。若 `p_t` 是 run share、`Y_t` 是每 run 的 pair yield，则 pair share 精确满足
`q_t=p_tY_t/E_p[Y]`；pair sampling 本质上是按 opportunity yield 的 size-biased reweighting。total variation 的变分刻画
进一步说明，当前 `TV(p_run,p_pair)=0.337082500713674` 正好是 pairing 对任意 `[0,1]` task-level 指标可造成的最大
聚合偏移，即 33.71 pp 的 sharp worst-case design leverage。它不是某个 predictor 已观察到的 accuracy 差，closure 后仍须用
真实 task vector 计算实际偏移。

### 2.1 新增：结果前冻结两级聚合影响审计

为了避免 closure 后把结构 pair 产率和 truth/evaluability filtering 混成一个机制，我们已经正式冻结两级链：eligible runs
`R_t` 先产生过滤前 structural exact-common pairs `S_t`，再保留 informative/evaluable pairs `I_t`。closure 后对每个
arm 和 paired contrast 都必须把 pair→run 聚合变化精确分为 structural-yield 与 informative-filter 两段，并分别报告
`range(task metric) × TV(task weights)` sharp bound。

该审计只有在 first-960+closure、frozen registry、exact common support 与 full task universe 同时成立时才能运行；否则固定
失败，禁止删除零支持任务。alternate weighting、decomposition、subgroup 或 sign flip 均不能挽救失败 primary。fresh Linux
focused/full=`17/1064 passed`，18/18 independent checks PASS，verifier 双跑逐字节一致；源码提交为 `f970262`。

相关理论边界也已收紧：informative cluster size 与 cluster/individual weighting 已有统计学先例，不主张重加权恒等式本身
新颖。可主张的是在真实 MLE-agent chronological sibling benchmark 中的 outcome-blind 证据，以及揭盲前冻结的两级机器
审计。它仍不是 predictor accuracy 或 search utility 正结果。

公开结果包随后从 GitHub 精确提交新建 fresh Linux worktree，post-push focused/full=`20/1067 passed`；inner manifest
全通过，两个 verifier replica 与 committed receipt 三者逐字节相同。formal `SHA256SUMS` hash=

### 2.2 新增：task-balance guard 的首次前瞻核验

把在 `7cda` 结果前冻结的 25% dominant-task pair-share guard 应用于后续 `8579` 快照。新加入 27 runs / 120
structural pairs，其中 27 个 OSIC、93 个非 OSIC。冻结公式精确预测 `657 + 3×27 − 93 = 645`，独立从当前 per-task
counts 复算同样为 645，因此结构债务净减 12。descriptive pair-HHI 与 run→pair TV 也分别下降约 0.00252 / 0.00922。

这不是无条件好消息：OSIC share 仍为 30.85%，25% cap 失败；并且 debt 清零前新增了 OSIC pairs，旧 guard 的
“暂避 OSIC”即时动作没有遵守。自然摄取没有随机化，不能写成 guard 造成改善或 producer compliance。HHI/TV 又是在运维
阶段见过概要后才正式封存，只能作 descriptive secondary，不能挽救 cap。

chronology audit 还纠正了一个过强检查：新 ledger 不是旧文件的 byte-prefix，因为 2 个按冻结时间全序更早的新 runs 插到旧
provisional tail 前；但所有 339 个旧 run_id、旧相对顺序和同 ID 行内容全部保留。正式 invariant 因而是 set inclusion +
subsequence + row identity。首次 byte-prefix failure、runner grep 错误与跨 Python 普通 float sum 末位不一致均被保留；后者
用 `math.fsum` 修复后，fresh Linux focused/full=`15/1080 passed`，双 producer/verifier 逐字节一致。

### 2.4 数据与问题

上述结构轨迹分析使用 first-960 前瞻 cohort 的固定 `7cda` outcome-blind 快照：

- 339 个 eligible physical runs；
- 10,196 个 eligible endpoints；
- 2,635 个真实 sibling structural pairs；
- 30 个任务。

我们比较了 provisional first-240 与当前 339-run 快照，问题是：随着新 runs 加入，语料在 run 层和 pair 层是否都变得更加均衡？

### 2.5 核心结果

| 统计口径 | First-240 | 当前 339 runs | 变化方向 |
|---|---:|---:|---|
| Run-weighted 最大任务占比 | 10.83% | 9.14% | 更均衡 |
| Run-weighted inverse-HHI | 17.87 | 20.46 | 多样性提高 |
| Pair-weighted 最大任务占比 | 17.15% | 31.23% | 更集中 |
| Pair-weighted inverse-HHI | 12.04 | 7.37 | 多样性下降 |

当前还有两个直接诊断量：

- run-weighted 与 pair-weighted 任务分布的 total-variation distance 为 `0.3371`；
- pair 主导任务的 pair share 相对其自身 run share 被放大 `5.042` 倍。

因此，“新增 physical runs 的任务覆盖更均衡”并不推出“pairwise benchmark 的实际任务权重更均衡”。直接报告 pair-micro accuracy，会让更容易产生 sibling pair 的少数任务获得更大的隐式权重。

### 2.6 排除简单伪解释

2,635 个 pairs 来自 2,593 个不同的 physical decision-parent groups。相对于每个 parent 一个 pair 的基线，仅有 42 个额外 pairs，占全部 pairs 的约 1.59%。因此，当前集中现象不能简单归因于少量 parent 被反复枚举出大量 pairs。

该分析经过以下验证：

- producer 与 independent verifier 双实现；
- 不同 `PYTHONHASHSEED` 的确定性复跑；
- 正式 Linux 环境 focused/full tests；
- 提交后从精确 Git commit 重建并逐字节核对。

这是一项正面的 benchmark-design 结果，但它不是新的 critic accuracy 提升，也不应包装成方法模型已经取得突破。

## 三、结果前冻结统一 estimand panel

结构图谱表明，不同聚合方式可能改变总体趋势。为防止揭盲后选择有利统计口径，我们已经在读取任何 prospective outcome 或 prediction 前冻结通用 predictor benchmark 的报告契约。

### 3.1 通用 headline

`task_macro_parent_macro_pair_accuracy`：

1. 先在同一 physical decision parent 内平均 pair credit；
2. 再在每个 task 内平均 parent；
3. 最后对 tasks 等权平均。

### 3.2 强制并列、不得用于挽救 primary 的敏感性指标

- task-pair macro；
- task → run → parent → pair macro；
- pair micro。

所有 predictor arm 必须在完全相同的 pair support 上比较，并先在 pair 层计算 arm difference，再按同一层级聚合。任何 alternate aggregation、truth channel 或 subgroup 都不能用来挽救失败的既有 primary。

### 3.3 推断方法

- 20,000 次 task bootstrap；
- 固定 seed `20260901`；
- leave-one-task-out；
- physical-run clustered sensitivity；
- 禁止把 pair-i.i.d. confidence interval 作为 headline。

该 panel 只统一论文中的 generic predictor table，不覆盖此前已经冻结的实验 primary：clean scaling 继续使用 task-macro pair primary，component breadth 继续使用 task-macro parent-macro primary。

## 七、当前判断与下一步

### 已经增强的部分

- 数据集与 benchmark 的方法论故事显著增强；
- pair weighting 的结构偏差是可复现的正面发现；
- 结果前冻结 estimand，降低了事后选择统计口径的风险；

### 尚未确认的部分

- 目前没有新的 prospective critic accuracy 结果，因为 first-960 和 closure 尚未完成；
- 学长观察到的 model-size scaling 仍是当前最强的方法侧正信号，但旧实验存在 cross-config mixing、outer-test 周期评估和部分训练未正常结束等限制；
- 不能用结构分析本身声称 critic 已经有效提升搜索质量。

### 推荐后续顺序

1. 继续 append-only、credential-first、outcome-blind 摄取，完成 first-960 与独立 closure receipt；
2. 保持固定 scorer/WL extension 只写 prediction escrow，不读取准确率；
3. 对学长的新训练脚本先做 split、checkpoint-selection 和停止原因审计；
4. 若要确认 scaling，使用 future exact-stratum producer、仅由 train-run dev 选择的新 checkpoint，以及从未触碰的 frozen cohort；
5. closure 后严格按已经冻结的 primary、estimand panel 和 inference protocol 揭盲，失败时不使用 alternate aggregation 救结果。
