# Hindsight 方案演变

目标是把搜索中积累的调试和方案改进经验，转成额外的训练回答。
例如原轨迹先提出方案，经过几次 debug 才跑通，随后又试出了更好的方案；
hindsight 希望让模型在最初输入下就能利用这些经验，提出更完整的解法。
当前实现与使用方法见 `hindsight.md`，代码设计见 `hindsight_impl.md`。

## 1. 直接重写思考：容易变成答案讲解

最初让模型阅读完整轨迹和跑通代码，直接写一段思考，再配上原来的跑通代码。
这样能保留已验证的程序，但生成内容更像回顾和讲解已知答案，部分样例还丢失了
思考与代码之间的独立计划。它与 policy 从输入出发、逐步形成方案的回答形式有差距。

因此改为先提炼经验，再让 policy 用自己的原生 thinking 完整解题。

## 2. 提炼 hint 后生成，再换回旧代码：回答内部不一致

第二种做法先把轨迹提炼成详细工程建议（hint），临时加入原始输入，让 policy
生成完整思考、计划和代码，最后将代码换成来源轨迹中已经跑通的程序。

问题在于 policy 会根据建议调整模型、预处理、训练或推理方案。换回旧代码后，
思考和计划可能仍描述新方案，与实际保存的程序不一致。因此放弃代码硬替换，
保留同一次生成的完整回答。

也比较过只给文字经验与额外提供完整来源代码。小规模对照中，附代码经常使新程序
在文本上更接近来源，但相似度无法说明代码正确性或训练收益。当前默认只给文字
经验，附来源代码保留为实验选项。

## 3. 当前重写方式：完整回答与来源质量分开记录

当前流程是：轨迹提炼 hint → 原始输入临时加 hint → policy 完整重新解题，
训练时恢复原始输入，原样保留新回答。思考、计划和代码来自同一次生成。

生成阶段继承来源跑通节点的 CV 分数，用于区分经验来源质量；新代码的实际表现
通过独立执行评估流程验证。来源标签与执行结果分开记录，避免把继承分数当成
新程序实测成绩。合成数据单独分组、计算 advantage，筛选后再与原数据合并。

树结构上，新回答作为原父节点下的额外方案，保留必要的祖先关系以追踪来源。
曾将祖先锚点各自作为根的做法会丢失原树层级，因此改为保留祖先链。
这棵树用于来源索引；新回答的执行历史由后续评估产生。

## 4. 用模型审查 CV：成本和判定不确定性过高

曾尝试让模型检查跑通代码是否利用评估漏洞抬高 CV，例如验证标签泄漏、训练与
验证重叠、用正确答案填补预测。目标是过滤虚高标签，同时保留正常但效果差的方案。

为减少误杀，又给初轮拟拒绝的方案增加独立复核，并尝试开启更充分的模型思考。
复核确实改变过部分判定，但也出现理由与最终布尔结论不一致的情况；只复核
拟拒绝项也无法弥补初轮漏检。

这套机制引入了额外模型调用和不稳定的筛选决定，因此最终从生成流程移除，
直接按原树中已跑通的轨迹和 CV 改进关系选择候选。warmup test 在独立流程维护。

## 5. 当前实验安排：分开控制两类经验

调试经验与方案改进经验的来源不同：前者来自同一方案从报错到跑通的过程，
后者来自后继方案相对前一方案的 CV 提升。为便于分别验证和后续调整，入口支持
只生成 debug hindsight，或同时生成 debug 与 improve hindsight。
具体模式和运行行为见当前使用文档。

## 6. 一次性完成的处理方式

将批量重写简化为一次完整运行，输出只保留 run metadata 和两种 journal。
案例生成只保存 metadata、合并的调用 trace 和节点，执行对照按显式 prepare/evaluate
两步进行。原先为短 allocation 添加的请求缓存、重启记录和整树评测入口已移除。
目的是维持代码简洁，以免这个中间实现消耗太多精力。
