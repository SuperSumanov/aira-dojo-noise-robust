# Hindsight 方案演变

当前实现、数据格式与运行命令见 `hindsight.md`。这里解释为什么改变重写方式。

## 1. 目标：把后续试出来的经验带回初次动作

一个 episode 从 implement（journal 的 `draft`）或 improve 开始，接上修错误的
debug 链，到跑通为止。例如：

```text
parent → draft A → debug B → debug C（跑通）→ improve D（更好）
```

第二步用 A/B/C 的调试经验重新回答 A 的输入；第三步用 D 的更好方案重新回答
A 的输入。第三步的目标也可以是 improve，它根据原树上的前后 episode 选候选。

新回答是原 parent 下的额外 episode。原 B/C 仍属于原 A，不接到新回答后面。
因此，“输出正确代码后还修旧 bug”是替换原 episode 首节点并保留旧 debug 后继
才会出现的矛盾，不能用来否定同父节点新增 episode 的方案。

## 2. 第一版：直接交付重写后的 thinking

最初让模型看完整调试轨迹和跑通代码，直接写一段 thinking，再配上跑通代码。
提示词要求一段约 300–800 词的总结。

实际出现的现象是：思考像在讲解已知答案，开头直接介绍任务、方法和关键挑战，
然后逐项解释如何实现；有的输出还丢掉 think 和 Python 之间独立的 plan。

这和生成任务有关。重写模型自己先 reasoning，再给最终回答；程序取它的最终
回答放进 policy 的 think 位置，提示词又要求总结，训练样本就更像“回顾并讲解
答案”，而不是“根据输入提出方案并实现”。这是样例和提示词支持的工程判断，
不等于已经证明模型有无法纠正的内在偏差。

## 3. 第二版：hint → 完整生成 → 换回跑通代码

为恢复解题过程，将重写拆成两次调用：

```text
完整轨迹 → 详细 hint
原 prompt + hint → policy 完整生成 think / plan / code
最后把 code 换成原轨迹跑通代码
训练输入移除 hint
```

hint 提供 API、张量形状、标签处理、验证/推理对应关系、训练参数和资源生命周期
等具体经验。完整生成使用 policy 的原生 thinking，独立 plan 也随回答一起产生。

但最后一步又拆开了本来一致的回答。模型会根据 hint 自行改变模型、训练循环、
预处理或推理策略；把新 code 换回来源 code 后，think/plan 仍在描述模型刚提出的
方案，未必对应被换进去的代码。第二步和第三步都可能出现这种回答内部的冲突，
其中第三步本来就要吸收方案改进，更不能假设一定逐字复现来源程序。

### 是否把完整来源代码一起放进 hint

曾比较“只给文字经验”和“额外附整份跑通代码”。小规模对照中，附代码确实
经常让新 code 在文本上更接近来源，但不保证逐字复现，也不保证思考中的每个
决定都与来源一致。文本相似度只能说明改写程度，不能代表正确率或训练收益。

所以继续加约束来挽救硬替换并不划算。当前默认只提供文字经验；附代码作为可选
实验保留，两种方式都原样保留完整新回答。

## 4. 当前方案：保留完整回答，继承来源质量

最终采用：提炼 hint → 原 prompt 临时加 hint → policy 完整重新解题 → 原样保存
新 response，训练 prompt 恢复原输入。think、plan 和 code 来自同一次生成。

新代码未经执行。继承来源最终跑通节点的 metric，是为了区分经验来源的质量，
供合成候选组内部计算 advantage；它不表示新代码已经实际取得该分数。因此树中
明确保留重生成、未执行和标签继承标记，清空分析、终端输出、退出码和官方分数。

合成数据单独分组、单独算 advantage，严格筛 `advantage > 0` 后再和原训练行
合并。进入共享数据流程后，行格式与普通数据相同；来源追踪通过保留的树完成。

## 5. 树结构与上下文的一致性

曾有一个中间实现将每个父节点锚点单独作为根，导致来源树层级丢失。当前沿原树
补齐必要祖先的 parents/children，祖先锚点不包含原代码、模型调用或执行结果；
生成结果作为原 parent 下的额外 proposal，原始数据继续单独保存。

保留来源树也保留了一项限制：原 prompt 可能引用旧祖先的代码、报错或 memory，
这些内容不会因新回答而重生成。树用于索引来源，而不是重放新代码的执行历史。
这与“把旧 debug 后继接到新回答下面”是两个不同的问题，阅读和使用时需要区分。

## 6. CV 审查：从一次判定到拟拒绝项复核

两轮审查是针对初轮模型可能误判而增加的设计。审查用于过滤被评估漏洞抬高的
CV 标签：例如把验证标签当作预测、训练验证重叠、用正确答案补空预测。
低分、普通推理错误和训练不足仍然能提供有用的质量标签，应保留。

第一轮关闭 thinking，要求给出代码依据和 `untrustworthy`。仅对初轮准备拒绝的
episode 增加第二轮：开启 thinking，给出初轮理由和代码，让模型主动寻找反证，
尤其区分“标签用于正常计算指标”和“标签参与生成预测”，以及正常上下文处理与
答案泄漏。复核结果替代初轮结论，确认拒绝后才剪掉来源起点和后代。

复核采用自由文本生成后解析 JSON，而非生成时的 JSON grammar，给思考与最终
判断留出空间。当前代码和测试能确认这一实现选择；保留的报告不能单独证明它比
受约束生成更准确，也不能还原每项设置调整的具体实验时间。

2026-10-30 全流程留下的 17 份 run 报告共记录 319 个来源 episode：初轮拟拒绝
19 个，复核最终拒绝 8 个，其余 11 个改为保留。这说明复核实际改变过筛选结果，
并不等于 11 个都是被纠正的误判，也不是数据集上的准确率测量。

检查报告时还发现一个具体限制：某条复核的文字仍认为“空预测回退到正确答案”
会抬高 CV，返回的 `untrustworthy` 却是 `false`。当前程序只校验字段类型和非空
理由，最终按布尔字段决定保留或拒绝，没有检查理由与结论是否一致。
因此历史数据中的“复核后保留”只能解释为模型的最终布尔决定。
建议后续单独检查审查结论的一致性及其对筛选的影响；本次拆分 client 入口保留
已有判定语义和缓存，不悄悄更改历史标签。

## 7. 客户端按阶段拆分入口

原先 `ask(stage, messages)` 同时判断审查、复核和两种 hint 的输出结构、thinking
设置、缓存路径及重试方式，改动某一阶段时需要检查多处分支。
现在公开 `audit`、`audit_review`、`debug_hint`、`improve_hint` 四个入口，分别确定
阶段设置；底层只共享请求发送、JSON 解析校验、重试和缓存机制。
完整 policy 回答仍走独立的 `generate`。详细设计见 `hindsight_impl.md`。

## 8. 审查开启思考，取消额外的默认输出上限

2026-11-01 将初轮 audit 改为开启 thinking，与复核一样使用 medium，并取消生成时
的 JSON grammar，返回后解析和校验 JSON。两轮的区别回到任务本身：初轮找评估
漏洞，复核对拟拒绝理由寻找反证。

先前关闭初轮 thinking 是节省开销的工程默认值，没有对照实验证明更适合这个
27B 模型。评估审查需要追踪标签、预测与指标的数据流；初轮漏掉的问题不会进入
只针对拟拒绝项的复核，因此优先让初轮完成充分推理。

同时移除 audit 的 4096、复核的 8192 和完整生成的 32768 默认输出上限。
这些固定预算没有经过模型上的充分验证，可能截断正常思考和代码。
完整生成仍继承原 operator 显式记录的 `max_tokens`；服务端自身的生成默认值和
上下文限制仍然生效。hint 提炼的参数保持原样。

审查缓存版本升至 4，主流程缓存版本升至 8，避免同目录重跑直接复用旧设置的
审查或整树完成报告。这次修改尚未对原数据重新进行完整生成和筛选。
