# 27B 滚动 online policy 的 E2E 结果（截至 2026 年 10 月 16 日）

这次整理 10 月 13—15 日三个 checkpoint 在 5 个任务上的结果。数据分散在不同日期的目录中，按任务重新对齐；统一读取大写 `json/JOURNAL.jsonl`，覆盖第一轮 draft 尚未成功的 run。当前快照共有 **95 个 run 目录，95 份大写 journal**。文中的日期表示实验归档批次，实际启动时间记录在各 run 的配置中。

## 0. 硬件和编排

1. 第n天拿第n-1天的训练checkpoint生产数据，然后数据整理加入到n+1天的训练之中。为了保证所有gpu持续运行，交错并行两个滚动训练，一个用测试集score做奖励，一个用agent自己生产的cross validation得分做奖励。
2. 推理和数据生产用14卡3090+6卡2080，训练用4卡H200，每天的训练基本上6-7个小时就能完成，训练完成后H200也接入推理和数据生产，而且每张承载4个任务。
3. 上述资源来自3个不同集群，目前靠人力来启动任务，搬运，和汇总数据。

## 1. 先说结论

1. **滚动 score 续训的收益集中在部分任务。** 1015 相对 1013，dog 和 tgs 的主指标提高，BMS 和 champs 下降，chaii 基本持平。dog 的 S2 略低于 `random` 原模型基线。正文同时列出有效 run 数和同 seed 对比。
2. **metric 奖励分支在三个任务上优于第一轮 score 分支。** 1014 在 champs、dog、tgs 上的主指标高于 1013，在 chaii、BMS 上较差。tgs 的选解损失缩小；BMS 则出现了截短标签后计算 CV 的目标偏离。
3. **BMS、champs 的 debug 链变长，dog、tgs 缩短。** BMS 每条 episode 的平均 debug 次数从 1013 的 5.43 增至 1015 的 9.00，champs 从 3.85 增至 6.11。
4. **找到了三种“高内部指标、低官方分”的工程原因：提交编码错误、验证目标偏离、分析器猜分。** 其中 BMS 的真实 CV 为 75.1825，分析器却填成了 1.75。但看思维链和代码都没找到明显reward hacking的证据。
5. **BMS 出现了“拒绝跑得通但效果差的解，继续 debug”的行为。** S2 seed 2 因欠拟合被判 buggy，尽管程序已完成并生成合法提交。原模型中也有类似记录，训练对这种判断倾向的影响值得单独测量。

### 2.2 指标与统计口径

沿用 `src/dojo/analysis_utils/journal_to_fig.py` 的六条曲线：每行取 `data`，官方分读 `metric_info/score`，方向读 `metric_info/is_lower_better`。BMS、champs、dog 的分数已取负，本文所有数字统一为**越大越好**；champs 原始 mean log MAE 可以为负，取负后相应为正。

- **`avg_selected_score`，主指标**：每个 run 按最高内部 `metric` 选节点，取它的官方分，再对有效 run 求均值。内部指标并列时保留先出现的节点。该值由脚本按选解规则重建。
- **`max_score`**：跨所有 run、所有日志节点见过的最高官方分，包含 agent 接受和拒绝的节点。
- **`avg_max_metric`**：每个有有效内部指标的 run 的最高内部指标，再求均值。它反映 agent 记录的验证表现，具体含义随代码的验证划分、指标实现和目标长度变化。
- **主指标有效数 / journal 数**：有选中节点且官方分有效的 run / 找到大写 journal 的 run。均值由这些有效 run 计算，覆盖率单独列出。

### 5.2 训练目标到底奖励了什么

代码依据是 `src/mle_policy/src/data/big_journal.py`、`journal.py:resolve_episodes`、`to_grpo.py`，以及 `src/verl/my_recipes/mle_policy/src/trainer/ppo/offline_ray_trainer.py`：

1. 每个 episode 取**第一个被 agent 接受的终点**的 score 或 metric，转成 episode reward。
2. 把环境一致、修剪后初始 prompt 相同的 episode 放进一组，计算 `A = (reward - 组内均值) / 组内标准差`。这里 A 就是该 episode 相对同组其他尝试应该被鼓励还是被压低的权重。
3. episode 内每次 LLM 调用，包括 debug 和默认保留的 analysis，拆成独立训练行，**都复制同一个 A**。没有解决的 episode 也进组，默认奖励是同组最低有效奖励再减 1；没有对比信号的组会跳过。
4. verl 直接读取已有 prompt/completion/reward/advantage 进行离线更新。更新完成后，用新 checkpoint 去真实环境生产下一批数据。

这套训练优化的是**每条 proposal→debug episode 的终点质量**，episode 内各调用共享终点奖励。固定时间预算下的最终提交质量，还取决于 episode 耗时和整场搜索能完成多少次尝试。

这个目标给长链留下了三种激励：

- 奖励按终点质量计算，debug 次数、执行时长和搜索预算的显式成本为零。一个很慢才成功的解，可能获得比快速低分解更高的奖励。
- 整条链共享终点的正权重，前面写坏代码、错误否决等动作也可能一起被强化。
- 当前按调用拆行，一条长链通常贡献更多训练行。默认 actor 配置为 `token-mean`，实际权重还与回答 token 数及运行配置有关。这里的长链偏重来自训练样本和 token 的占比。

### 5.3 “嫌解不够好，所以继续 debug”的直接例子

**BMS，S2，seed 2，step 9**：`exit_code=0`、`metric_info/valid_submission=1.0`，官方原始距离为 **82.13637**，但 `is_buggy=True`。analysis 将“欠拟合、预测没有意义、训练轮数和模型容量不够”当作 bug，建议换更复杂的架构或增加训练。前面的 step 7、8 也做了类似否决，官方距离为 83.26155、82.71853。这个 run 生成过合法提交，所有节点却都被 agent 拒绝，最终主指标缺失。

这条记录展示了“submission 能交但不够好，被拒绝后延长 episode”的过程。BMS 原模型中也存在类似行为，后续可以直接测量各 checkpoint 将低分解判为 buggy 的倾向。`exit_code=0 + valid_submission + buggy` 的记录还包含数值问题、被代码捕获的异常和旧提交残留，具体原因需要结合 analysis 与执行输出分类。

这类候选记录在 BMS 原模型 / S1 / M1 / S2 中分别为 **13/79、18/45、4/50、7/40 个操作节点**；champs 为 **10/90、5/63、10/54、15/64**。这些计数提供了逐条分类的入口，BMS 与 champs 的变化模式也各有差异。

## 6. 高 CV、低官方分：逐例拆开看

下面从代码、执行输出和指标提取三个环节解释分数差距，并用小输入验证编码错误、核对标签截短和猜分记录。

### 6.1 tgs S1 seed 1：improve 产物中的编码错误在 debug 后沿用

按内部指标选中的 step 26：CV **0.7729**，官方分 **0.0756**。代码在 `rle_encode` 中用下一段的开头 `positions[breaks]` 作为当前连续区间的末点，将本来分开的像素连起来；后续过滤重叠区间时又会扔掉一部分区间。正确末点应是当前段的最后一个像素。空 mask 还被写成 `"1 1"`，相当于强行预测一个像素。

把日志里这个函数单独取出，在 101×101 的 mask 上放两个分开的像素 `(0,0)` 和 `(3,0)`：

- 正确的列优先编码应该为 `1 1 4 1`；实际输出为 **`1 4`**。
- 空 mask 应输出空字符串；实际为 **`1 1`**。

验证直接在预测 mask 上算指标，提交阶段才调用编码函数，因此 CV 绕过了这层错误。对提交做编码—解码往返检查，可以直接捕获它。

沿父子关系检查，episode 根节点 **step 24（improve）已经包含这个错误，step 25、26 的 debug 沿用了它**。这个例子定位到了提交路径上的确定性 bug；修复后的官方分变化可以通过重算提交进一步验证。

### 6.2 BMS M1 seed 1：CV 在截短标签上计算

选中的 step 23：CV 原始距离 **15.0678**，官方原始距离 **90.02769**。代码显式设置 `MAX_TARGET_LEN = 45`，数据集用 `str(self.labels[idx])[:self.max_len]` 截断标签，验证函数又从这份截短后的 target 重建字符串来计算距离。因此 CV 测量最多前 45 个字符的距离，官方评测则使用完整 InChI。

该截短在 step 21（improve）中就存在，22、23 的 debug 沿用。这是一个**实测指标与官方任务目标偏离**的例子：metric 奖励会直接消费这个偏离后的数值。下一步应在完整标签上重算验证距离，测量截短对分差的具体影响。

### 6.3 BMS S2 seed 1：内部最优 1.75 是分析器估计出来的

选中的 step 20：`metric=1.75`，官方原始距离 **76.07505**。analysis 写明它根据“被截断的输出中训练 loss 约 1.99”和对架构典型表现的判断，**估计** validation distance 约为 1.75。

训练 loss 和 Levenshtein distance 是两个量。这里的内部指标污染来自**负责读输出的 analysis 模型猜分**。这一问题出现在按 score 训练的 S2 中，也会影响使用同一指标提取流程的 metric 奖励数据。

同一节点的完整 `_term_out` 明确写着：两个 fold 的验证距离为 **75.2236、75.1413**，均值 **75.1825 ± 0.0412**，与官方距离 76.07505 接近。这个例子的巨大分差主要由**输出截断后分析器填错指标**造成。完整输出中已经包含正确数值，修复指标提取即可消除这处虚假的高 CV。

综合来看，**M1 在 tgs、dog、champs 上的选解损失缩小，同时存在提交实现、验证目标和指标提取三类可靠性问题。** 这些具体工程环节为解释分差和修复奖励提供了直接入口。
